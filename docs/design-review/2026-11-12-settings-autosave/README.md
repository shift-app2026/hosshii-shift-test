# PR #8：設定の即時自動保存と閉じるボタンの削除

文字・配置の追加調整を `75d6ae1` で先に完了し、その後、ユーザーが追加承認した保存改善を実施しています。[文字・配置の比較一覧](../2026-11-12-small-alignment/README.md)

## 保存処理の変更

- 設定フォームのinput/changeで、最新のフォームをconfigへ同期し、そのイベント中に既存の保存関数で同期保存します。500msの待ち時間は給与表示の再計算だけに残し、保存を待たせません。
- 書込みと読戻し検証に成功した場合だけ保存済みと判断。保存値の形式・キー・給与計算・バックアップ形式は維持しています。
- 同一画面の保存は同期処理で順に完了します。古い値を持つ遅延保存を残さず、連続入力後に古いタイマーが上書きしないことを検証しました。
- 保存できなかった入力はフォーム・メモリに保持。失敗警告と設定上部の「再保存」を表示し、再保存の成功時にだけ警告欄を隠します。
- 未保存状態が残っている場合は、下部タブへの移動、pagehide、beforeunload、非表示化でも保存を再試行します。主な対策は入力時の同期保存で、終了イベントだけには依存しません。
- 時給行を追加した場合も、その行を描画した後に保存します。
- 時給行削除は、保存成功後にだけ一覧を描画し直し「削除しました」を表示。失敗時は行を元に戻し、入力欄と登録状態を保ち、「削除できませんでした」と表示します。
- 検証後、「閉じる（設定を保存します♡）」を削除。通常は下部タブで自由に移動できます。

バイト先名の新規登録・変更や時給行の「登録」は、従来の明示的な登録・検証操作を維持しています。入力だけで新しいバイト先を勝手に登録しません。登録／保存ボタンの金文字・白文字の仕様も維持しています。

保存先自体が利用できない場合、入力は開いている画面に保持しますが、保存不可のまま端末を終了した場合まで保持を保証するものではありません。警告が出た場合は画面を閉じず、「再保存」で完了させてください。複数のブラウザー窓から同時編集するための新しい競合解決機構は追加していません。

## 過去のお給料・適用開始日

元のアプリには、時給の「適用開始日」や時給履歴を保存する項目がありません。従来から現在の勤務先の時給設定を使って過去の日付も再計算します。今回、この計算仕様は変更していません。

2024年のうるう日、2025年元日、2026年10月・11月の通常勤務・日またぎ・有給、計12ケースで、同じ設定とシフトから得られる金額が修正前と一致することを確認しました。[結果](history-results.json)

保存改善の[承認済み差分](../../../tests/approved-settings-autosave.json)を正確に戻すと、表示調整完了時の全スクリプトと一致します。計算・日付処理・シフト登録・認証・体験・課金・バックアップのコードは変更していません。
