# アプリd3f33a4とバックアップAPI候補1e3f0e5の照合

結論: 無料体験用の保存・復元契約は一致。アプリ修正の重複適用は不要。実サービスへの接続合格ではありません。

## 版と作業範囲

- アプリ: `verify/trial-launch-isolated` / `d3f33a4322b756e96530c39f962b7b4293dadc73`。
- サーバー候補: `1e3f0e57a2f21e609b9040914d46686de0509250` の `review/backup-prelaunch-fix/` のみを、そのままコピー。
- 別の統合検証ブランチ: `verify/backup-contract-integration`。
- `client-guard.patch` は資料として保持するだけで、適用していません。クラウド保存入口と復元入口の2ガードはアプリに既存。アプリはさらに共通要求・応答後の再検査・期限切れ端末書き出し経路を持っています。
- index.html、prelaunch-core/model/ui.js、CSS、認証・計算の実装はd3f33a4から変更していません。サーバーの単一/2ファイル版も共有版から変更していません。
- 連携側の固定参照core/modelは末尾空行が1行多いだけで、実装は一致。manifestの17対象ファイルすべてのハッシュ一致（SHARINGとmanifest自体は対象外）。

## 照合結果

|項目|結果|
|---|---|
|要求|アプリのPOST JSON `{action:'save'|'load',idToken,backupData?}` とAPIが一致。所有者はサーバーが検証したLINE subjectを使用。|
|成功応答|saveのHTTP200+`ok:true`、loadの`ok:true,backupData,updatedAt`が一致。アプリは余分な応答項目を要求しない。|
|エラー|401/403/404/500等は非成功として処理し、APIのerror/messageを利用。期限切れ403で成功通知・ローカル上書きなし。|
|schemaVersion 2|外側とstate内のschemaVersion、format、config/shifts/monthlyGoal、job1〜3のpayHistory/payBaselineを双方が認識。payDraftも削除されない。給与設定の意味検証と旧形式移行は既存アプリが担当。|
|旧形式|v23/v77、v22/v77、v21/v76をAPIが無変換で返し、実アプリがパディング日付を正規化して復元。次の保存で新形式へ移行。|
|期限|無料体験終了時刻以上では双方がクラウドsave/loadを禁止。アプリがまだ利用可能と認識している場合でも、サーバー403で拒否され、バックアップ操作なし。|
|開きっぱなし|アプリの現在時刻ガードにより再読込なしでクラウド要求を止め、端末JSON生成だけを行う。既存の実タイマー/通信中期限到達テストはd3f33a4に含む。|
|端末書き出し|期限切れ時の既存「書き出す」はクラウドを呼ばず、端末用JSONの生成へ分岐。APIとは独立。|

## テスト

1. 共有サーバーテストをNode 24.22.1で再実行: **41成功・0失敗**。報告の38件+単一ファイル版の追加3件。
2. 実アプリのUI保存/復元関数と、共有createHandlerを組み合わせて **320px・375pxの計14ケース成功**。
   - 履歴・基準値・下書き・シフト・目標を含む新形式の往復。
   - 旧v21/v22/v23の読み込み→実アプリの移行→新形式での再保存。
   - サーバー期限切れ403で保存/復元を拒否し、保存内容・端末データ・保存日時を維持。
   - クライアント側の期限到達後は要求なし、端末書き出しは可能。
   - 別の検証済み本人に他人のバックアップが返らないこと。

LINE検証・DBはメモリ内の架空実装。ブラウザーのバックアップ通信を捕捉して実ハンドラーへ渡しています。実稼働想定の許可Originをテスト要求に明示的に設定しているため、ブラウザーの実CORSやプリフライトの結合検証ではありません。実LINE・Supabase・Deno・Androidの実機ファイル保存を合格とは扱いません。

[結果・ログ](integration-results/)。追加テスト: `tests/trial-launch/server-integration.cjs`。実行にはローカル静的サーバー（例8913）を起動し、`PRELAUNCH_URL=http://127.0.0.1:8913 node tests/trial-launch/server-integration.cjs` を使用します。

## 残作業・統合手順

1. 今回の別ブランチをレビュー。**client-guard.patchは適用しない**。アプリの追加変更は不要。
2. 隔離環境のフロントURL、Supabaseプロジェクト、LINEチャネル/LIFFを固定。バックアップAPIのOriginは `https://shift-app2026.github.io` 固定のため、隔離側の実Originへ合わせた検証用設定が必要。既存Cloudflare/ChatGPTプレビューのままでは許可されない。本番設定を緩めず、隔離コピーで調整する。
3. APIの `SUPABASE_SECRET_KEYS.default`、app_usersの同意・開始/終了日時カラム、app_backupsのbackup_data型とline_user_idのUNIQUE、RLS/権限、ゲートウェイのJWT設定を実環境と照合。クライアントはSupabase Bearer JWTを送らないため、入口と関数内LINE検証の組合せを確認。秘密値は出力しない。
4. サーバー候補は単一ファイル版 `hosshii-backup.single.ts` または2ファイル版の**片方だけ**を使う。実Deno/SDKの読み込み・型/実行確認をする。
5. 隔離環境への配置が承認された後に、実LINEの2アカウントで新旧バックアップの保存復元、本人分離、初回同意の21日起算・再送時の期限固定、期限切れと通信障害を実接続試験。line-trial-statusの実ソースは今回の成果物に含まれていないため、21日起算処理は別途確認が必要。
6. 検証結果を報告し、本番取り込み・マージ・デプロイは別途承認後に行う。

### 注意する仕様の境界

- 今回のAPIは**無料体験中だけ**を許可し、`purchased_at`だけでは解除しません。アプリには`paid`応答での利用許可経路が残っています。有料利用者のクラウド権限は将来のSquare/契約期限対応時に統一が必要ですが、今回の無料体験公開の対象外です。
- APIはJSON要求全体にUTF-8の350000バイト上限を持ち、超過時は413。アプリはエラーを表示して既存データを維持します。大容量の既存バックアップの再保存は、この上限に注意。
- 保存の認可時点はDB呼び出し直前。認可後のDBコミット時刻までの厳密な期限保証は今回の候補の範囲外です。送信済み操作をアプリ側で確実に取り消すこともできません。
- 旧形式で給与設定キーが欠けるデータは、アプリの読み込みよりAPI検証が厳しく拒否します。通常の新旧完全バックアップを往復試験しており、不完全な旧データを合格としたものではありません。
