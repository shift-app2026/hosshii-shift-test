## 現在のクライアントが要求する接続仕様

|対象|要求|
|---|---|
|利用状態|`POST /functions/v1/line-trial-status`、JSON `{idToken}`。同意確定時だけ `consentAccepted:true, termsVersion:'2026-10-29', privacyVersion:'2026-10-29'` を追加。再照会ごとにLIFFからトークンを再取得。|
|初回|`status:'new'` / `not_started` / `consentRequired:true` の場合は同意ゲート。サーバーは初回同意の原子的保存・重複リクエストの冪等性が必要。|
|試用中|`status:'trialing'` / `active` と有効な期限。期限キーは `trialExpiresAt` / `trial_ends_at` / `trialEndsAt` / `trialEndAt`。タイムゾーン付きISO8601を推奨。期限なしは入力不可。|
|期限切れ|`expired` / `blocked` / `past_due` が試用フラグより優先。期限時刻以上は入力不可。閲覧・書き出しは維持。サーバー時刻が期限判定の正本である必要がある。|
|バックアップ|`POST /functions/v1/hosshii-backup`、JSON `{action:'save',idToken,backupData}` または `{action:'load',idToken}`。成功はHTTP2xxかつ`ok:true`、復元は`backupData`オブジェクト。|
|新バックアップ|`{format:'hosshii-shift',schemaVersion:2,exportedAt,state:{schemaVersion:2,config,shifts,monthlyGoal}}` を履歴・基準値・下書き込みで保存。旧ルートキーだけの抽出は不可。|

**入口認証の確認が必須:** 現行クライアントは `Authorization: Bearer <Supabase JWT>` や `apikey` ヘッダーを付けず、LINE IDトークンをJSON本文で送ります。SupabaseゲートウェイでSupabase JWTを必須にすると、関数本体の前で401になる可能性があります。LINEトークンを検証する設計なら、その入口設定と関数内の本人確認が一致している必要があります。入口認証を無条件に外すことや、service_roleキーをブラウザーへ入れることはしないでください。
